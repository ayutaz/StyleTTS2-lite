# Unity向け日英TTS PoC 計画（新規ドキュメント）

作成日: 2026-01-14

## 1. 目的（Purpose）
- Unity単体（オンデバイスのみ）で動作する**高品質・低遅延**のTTSライブラリを日英対応で実現する
- 商用SDK販売を想定し、**GPL/AGPL依存を回避**した構成で提供する
- PoCとして、**モデル改良 + Sentis向けONNX化 + Unity統合**までの実現可能性を示す

## 2. 必要要件（Requirements）

### MUST（必須）
- **Unity内完結**（サーバー推論禁止）
- **Sentis 2.4.1**で推論可能（当面はSentis前提）
- **日英対応**（日本語・英語の発話品質を両立）
- **商用配布可能なライセンス**（GPL/AGPL依存を排除）
- **マルチプラットフォーム対応**（Android / iOS / Windows / macOS / Linux）

### SHOULD（推奨）
- 1秒未満の初回発話開始（低レイテンシ）
- 端末上での安定動作（OOMや発熱を最小化）
- 1つのUnity SDKで統合利用（API単純化）

### NICE TO HAVE（将来）
- スタイル制御（感情/話速/声質の操作）
- 低スペック端末向けの軽量モデル

## 3. 前提・制約（Constraints）
- **単独メンバー**で進行（アドバイザー支援は別枠）
- **予算**: 200万円（人件費以外に使用）
- **GPU**: RTX 6000 Ada 1台は無償、追加はRunPod等で調達
- **既存調査資産**:
  - piper-plus / uPiper / uZipVoice / 過去調査ブログ
  - StyleTTS2-lite / StyleTTS2 / Kokoro のコード・設計の調査済み

## 4. 基本方針（Decision）

### 4.1 モデル基盤の選択
- **学習コードが公開されている StyleTTS2-lite 系をベース**に改良
- Kokoro の構成思想（decoder-only / ISTFTNet / 軽量化）を設計に反映
- VITS 系は **日本語の精度限界が既に検証済み**のため除外

### 4.2 G2P方針
- **GPL/AGPL回避**が必須
- 英語は uPiper の独自G2P実装を参考に自前化
- 日本語は misaki/pyopenjtalk 等のライセンス確認を行い、問題があれば独自化
- 共通の**シンボル体系（phoneme set）**を統一設計

### 4.3 推論ランタイム方針
- **Unity Sentis 2.4.1**をUnity内推論の標準とする
- モデル分割とメモリ最適化（TextEncoder / Predictor / Decoder を分割してONNX化）
- iOS/Androidの推論スレッド・メモリ制約を考慮
- Sentisで未対応演算が出た場合のみ、**ONNX Runtimeをバックアップ候補**として検討

## 5. 実行計画（Phase Plan）

### Phase 0: 要件・設計確定（1〜2週間）
- 目的/要件/制約を再確認
- データ/ライセンスの整理（公開データ、内部データ）
- 目標指標（品質・速度・サイズ）を数値化
- **採用アーキテクチャの確定**（StyleTTS2-lite改造 + Kokoro参照）

### Phase 1: データ/前処理/G2P整備（2〜4週間）
- 日英データの統一フォーマット化
- 正規化/記号統一/phoneme set設計
- 英語G2Pを独自パイプライン化
- 日本語G2Pの法的確認・実装

### Phase 2: 学習パイプライン構築（4〜8週間）
- StyleTTS2-lite をベースに改造
- Kokoroの構成要素を取り込み（decoder-only志向/軽量化）
- ベースモデル学習（Ada 6000 + クラウドGPUを併用）
- 中間チェックポイントを評価

### Phase 3: 日英対応モデルの完成（2〜4週間）
- 日英の混合学習または二言語モデルの統合
- 速度・品質の評価（MOS/可懂度/誤読率）
- モデル縮小（量子化/蒸留/層削減の試行）

### Phase 4: ONNX化・Sentis統合（2〜4週間）
- ONNX変換（TextEncoder / Predictor / Decoder）
- Sentis 2.4.1 + Unity の実装
- 端末別ベンチマーク

### Phase 5: PoC完成・申請資料整備（1〜2週間）
- PoCデモ（Unity内完結の音声合成）
- 成果物の整理（技術資料・動画・仕様）
- 申請用の成果物としてドキュメント化

## 6. 成果物（Deliverables）
- `TTSモデル設計書`（アーキテクチャ + 改造点）
- `G2P仕様書`（英語/日本語の処理規則）
- `学習再現手順`（設定・データ・手順）
- `Sentis向けONNXモデル`（Unityで動く推論セット）
- `Unity SDK`（API・サンプル・デモ）
- `PoCレポート`（品質/速度/サイズ/要件達成度）

## 7. 評価指標（Metrics）
- **品質**: MOS / ABテスト / 誤読率
- **速度**: RTF（実時間比） / レイテンシ（初回発話）
- **サイズ**: モデル容量 / RAM使用量
- **互換性**: Android / iOS / Windows / macOS / Linux の動作確認

## 8. リスクと対策（Risks）
- **ライセンス問題**: GPL/AGPL依存を回避するため、G2Pと辞書のライセンスを先に精査
- **学習コスト超過**: 早期に小規模実験で見切り、フェーズごとに継続判断
- **Unity推論性能**: ONNX分割や量子化で対応、端末別最適化
- **Sentis未対応演算**: 最低限の演算子置換またはONNX Runtimeをバックアップ候補として検討
- **日英両立の品質低下**: 言語別バッチ/トークン設計で影響を分離

## 9. 予算・計算資源の使い方（概算）
- 無償Ada 6000を **PoC常時利用**
- 200万円は **追加GPU学習・検証・評価**に集中配分
- まずは低コスト設定でベースラインを確立し、段階的にスケール
